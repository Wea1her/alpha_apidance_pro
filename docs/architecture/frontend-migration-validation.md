# 前端迁移：压力测试与验收方案

日期：2026-09-13。

已完成：当前文件存储的受控并发复现、静态失效分析和架构一致性审查。

尚未执行：新 API、网页、PostgreSQL 任务系统的容量、延迟与恢复验收；这些组件尚未实现。下列指标来自已确认的设计目标，不是测试通过声明。

## 1. 已执行的并发复现

环境：Node.js v22.17.0。两个可复用子进程，共 12 次合成记录提交。数据全部位于新建的临时目录，不读取真实业务数据，不请求模型、Alpha 或 Telegram。

| 真实存储组件 | 顺序对照：预期 / 实际 | 受控交错：预期 / 实际 | 两次写入都返回成功 | 错误数 |
|---|---:|---:|---|---:|
| AnalysisArchiveStore | 2 / 2 | 2 / 1 | 是 | 0 |
| AnalysisTaskQueue | 2 / 2 | 2 / 1 | 是 | 0 |
| ProjectStateStore | 2 / 2 | 2 / 1 | 是 | 0 |

复现步骤：两个进程先实际读到同一份空文件；暂缓读取返回，让 A 完成写入；随后允许 B 根据之前读到的旧快照完成写入。最终保留 B，A 已获得成功回执的数据消失。

只控制了真实读取返回的时机，存储组件的校验、记录构造、写入与 rename 未替换。ProjectStateStore 用真实 `load → 修改 → save` 调用，证明调用方没有获得并发合并保护，不能把整体替换接口当作事务更新。

结论：进程内 Promise 锁与文件 rename 不足以保护多写入者的业务更新。多个浏览器只读本身不会造成这个覆盖问题，但拆出 API/worker、多实例或新增写入口后会暴露它。

这证明一种可发生的丢失更新交错，不表示生产发生频率，也不是吞吐压测。

复现脚本：[reproduce.mjs](probes/file-store-concurrency/reproduce.mjs)。完整结果及被测源码哈希：[result.json](probes/file-store-concurrency/result.json)。

在仓库根目录执行：

```bash
node docs/architecture/probes/file-store-concurrency/reproduce.mjs .
```

需要支持 TypeScript 类型擦除的 Node 22.17 或兼容版本。每次生成独立临时目录，输出实际结果位置；不会改写项目的 `data/` 文件。未来源码改变时以输出的源码哈希和实际结果为准，不把旧复现结论套到新实现。

## 2. 已确认的容量与体验目标

| 指标 | 目标 | 计量边界 |
|---|---|---|
| 同时在线 | 10 个独立浏览器会话 | 每个会话具有列表查询和实时连接；共享同一密码，服务端无法按人区分 |
| 保留数据 | 100 万条业务接收记录 | 分布于 90 天，含重复、过滤、未达门槛和通过记录 |
| 入站峰值 | 每秒 20 条，连续 60 秒 | 60 秒是本方案对“短时”的测试定义；模型任务可排队 |
| 列表查询 | p95 ≤ 1 秒 | 记录 API 请求与浏览器列表更新的端到端时长；不能仅用数据库耗时代替 |
| 状态可见性 | ≤ 3 秒 | 数据库提交可展示状态，到在线浏览器显示；不包含模型生成耗时 |
| 数据丢失目标 | ≤ 1 小时 | 故障时间与实际可恢复的数据时间点之差 |
| 服务恢复目标 | ≤ 2 小时 | 从开始故障恢复演练到数据校验完成、网页可用且后台恢复工作 |

记录测试服务器、负载客户端、网络条件、提交版本和样本数。起始服务器建议 2 vCPU、4 GB RAM、SSD；指标是否可达必须实测，不能凭规格推定。

## 3. 容量验收方法

1. 在隔离数据库生成 100 万条合成业务接收记录、10 万个账号，以及标准/深度报告、任务与投递历史。固定随机种子，混合普通账号和热点账号；保留重复、解析失败及分类失败后放行等边界样本。
2. 按真实索引与保留结构运行，不用缩减的内存数据替代。先测冷启动，再热身 2 分钟，执行 15 分钟混合查询。
3. 10 个独立浏览器会话持续在线（共享同一访问密码）。每个客户端平均每 2 秒发起一次查询，混合列表分页、账号精确搜索、星级/状态筛选和项目详情；同时维持 2 秒轮询刷新（首版实时机制，规划第 12 节 Q14，SSE 为二期）。
4. 背景持续接收每秒 1 条事件，中途以每秒 20 条持续 60 秒制造高峰，同时写入合成任务和投递状态。
5. 使用可控模型与 Telegram 适配器，分别模拟短分类、普通分析、慢深度分析与失败；不对真实模型或频道施压。
6. 捕获列表 p50/p95/p99、错误率、状态可见延迟、队列最老等待时间、数据库锁等待、内存和磁盘占用。入站成功提交计数必须与可查询记录数一致。
7. 在新增数据期间反复翻页，核验稳定游标不漏不重。对热点账号验证有序判定以及只创建一个首次标准、一个首次深度任务。
8. 执行 90 天清理和一次备份，确认交互仍满足目标、长期报告仍可读、正在投递的正文与线程引用完整。

负载生成可采用 Node 或 k6，浏览器交互采用 Playwright；在实现阶段固定版本和场景脚本。首次压测失败时先依据查询计划、锁等待和任务积压定位，再决定优化或增加资源。

## 4. 必须通过的故障验收

| 编号 | 注入条件 | 必须观察到的结果 |
|---|---|---|
| F1 | 两个 worker 同时领取同一业务意图 | 只有一个当前持有者，重复创建由数据库约束拒绝；其他任务不丢失 |
| F2 | 同一账号的后续 5 星事件先完成模型请求 | 持久化判定顺序保证首个符合规则的事件拥有深度任务，后续不能抢占线程 |
| F3 | 模型超时、worker 中止、租约过期后旧进程返回 | 请求有截止时间，任务可回收；旧执行代次不能覆盖新结果 |
| F4 | 标准或深度正文已经落库后 Telegram 失败 | 网页完整展示正文，后续补发不再次调用已保存正文的模型任务 |
| F5 | Telegram 长时间整体不可用，或讨论映射缺失 | 分析继续；投递进入依赖等待，不逐条耗尽预算；恢复后自动唤醒并补发 |
| F6 | Telegram 已收消息但本地回执丢失 | 记录不确定尝试，按已确认策略继续补发；允许重复但不能隐藏尝试历史 |
| F7 | 单条消息配置错误或重试预算耗尽 | 明确告警和待处理状态；网页投递重放（预览+二次确认+必填原因+幂等键，Q59）保持原意图和分片，并写审计 |
| F8 | 两个数据库事务乱序提交、连续轮询窗口交错 | 首版轮询（第 12 节 Q14）：连续轮询间数据变更不漏不重，实体版本号单调；二期引入 SSE 游标后再验收 outbox 发布顺序与同事务发布标记 |
| F9 | 浏览器断网、重复标签页、长时间停留后恢复 | 从持久化状态恢复并重取快照；不会重新触发模型或 Telegram；二期 SSE 游标过期补拉另行验收 |
| F10 | 90 天清理遇到长期报告或未完投递 | 外键不级联删除报告、任务和投递；来源摘要可读，原事件显示过期 |
| F11 | 数据库不可用、磁盘满、坏数据 | 显示数据或采集异常，不伪装成“没有项目”；未提交事件不计为安全保存 |
| F12 | 模型供应商鉴权失效 | 无效请求停止反复消耗资源；分类仍按既有策略标记异常并保守放行；生成任务等待修复 |
| F13 | 429 与可恢复错误 | 尊重等待时间并退避，记录真实物理请求次数；依赖等待不冒充模型失败 |
| F14 | 未登录或错误密码、改密码后旧会话 | 未认证请求被拒并受速率限制；改密码后全部既有会话与 SSE 立即失效（Q73），仅操作者当前会话保留 |
| F15 | 报告含 HTML、脚本或不安全链接 | 页面仅安全渲染文本/Markdown，不执行模型或上游提供的脚本 |

每个场景都保存事件 ID、任务 ID、投递 ID、数据库状态快照和时间线。只看到 HTTP 200 或进程仍在运行，不能算恢复验证通过。

## 5. 备份恢复演练

1. 持续写入带可识别序号和提交时间的合成事件，并生成报告和未完成分片投递。
2. 按部署策略生成加密备份并上传到服务器外，记录备份包含的实际数据时间点。
3. 模拟原服务器不可用，在空环境从服务器外副本恢复数据库、配置与程序，不读取原机数据目录。
4. 核验账号数、报告内容摘要、唯一任务约束、待投递分片及线程引用。全部旧会话失效（Q73），持密码者重新登录。
5. 检查最新可恢复事件与故障时间的差值 ≤ 1 小时；检查整体恢复 ≤ 2 小时。上传成功时间较新不代表备份包含的数据足够新。
6. 恢复后台，验证积压任务继续工作、已保存报告不重新生成；对可能重复的外部投递如实记录。
7. 演练备份上传失败和损坏副本，确认能告警并选择有效副本。没有通过恢复验证的文件不能算合格备份。

## 6. 切换与回退验收

- 用现有合成事件回归星级阈值、分类放行/拦截、失败保守放行、升星重复规则和深度一次性规则。
- 导入历史 JSON/JSONL 时只迁移事实，不编造缺失的原始事件、分类理由或生成时间；不发生模型请求和 Telegram 发送。
- 影子采集/判断阶段禁止产生第二套外部副作用；切换时核验只有一个激活业务执行者。
- 保留旧记录到新业务 ID 的映射；核验标准提醒仍指向原分析评论，深度报告仍对应首次合规 5 星的频道线程。
- 新数据库产生写入之后，回退必须保留这些增量；不能以直接启用旧 JSON 目录作为无损回退方案。
- 记录切换观察空窗。当前无法保证 Alpha 回放，不能声称所有上游缺失事件会自动补齐。

## 8. 已执行的容量基线（M5，2026-09-14）

执行环境：本机 Docker `postgres:16-alpine`（**不是**目标生产服务器），独立压测库 `daxinjiankong_bench`，
与测试套件分库（测试套件会重建 schema，曾直接打断压测）。脚本：`npm run seed:synthetic` 与 `npm run bench`。

**数据集**（seed=42，可复现；同 seed 两次生成结果一致，不同 seed 不同）：

| 项 | 值 |
|---|---|
| 账号 / 项目 | 100,000 |
| 业务接收记录 | 1,000,000（90 天窗口） |
| 判定记录 | 1,000,000 |
| 边界样本 | 重复 49,570；解析失败 10,087；分类异常后放行 19,681；已排除项目 200 |
| 生成耗时 | 76.5 秒（批量 5,000） |
| 表体积 | `inbound_events` 540 MB，`decisions` 334 MB |

**混合查询**（10 个并发会话，每会话每 2 秒一次，持续 30 秒，含列表分页/搜索/星级筛选/项目详情）：

| 查询 | p50 | p95 | p99 | max |
|---|---:|---:|---:|---:|
| 列表 | 7 ms | **768 ms** | 796 ms | 797 ms |
| 项目详情 | 11 ms | 15 ms | 16 ms | 22 ms |

**入站高峰**（目标 20 条/秒，持续 60 秒）：实际 **20 条/秒**，写入 1,199 条，
**写入计数与可查询计数一致**（1,199 / 1,199）。

### 8.1 压测发现并修复的真实问题

1. **账号搜索退化为全表扫描**：`lower(project_key) LIKE '%关键词%'` 无法使用 B-tree 索引，
   在 10 万项目上单次约 32 ms（`Seq Scan ... Rows Removed by Filter: 99200`）。
   已加 `pg_trgm` + GIN 索引（迁移 `0010`），同一查询降为 **3.5 ms**（Bitmap Index Scan）。
2. **列表 p95 的瓶颈不在 SQL 执行**：单项查询计划耗时均在 10 ms 量级，
   768 ms 的 p95 来自 10 个并发会话争抢连接池（压测客户端 `max` 有限）+ 单实例资源竞争。
   因此结论是：**查询计划与索引已满足目标，连接池大小与实例规格需在目标服务器上重测**。

### 8.2 必须如实标注的边界

- 本节数据是**数据层（repository 层）**，不含 HTTP 解析、前端渲染与浏览器网络。
  验收方案第 2 节定义的“列表 p95 ≤ 1 秒、状态可见 ≤ 3 秒”是**端到端**指标，
  需用 Playwright 在浏览器里另采；在上面的环境上不能宣称端到端已达标。
- 列表 p95 768 ms 相对 1 秒目标余量很小，且该数字受本机资源限制，**不得**作为容量承诺。
- 状态可见 ≤ 3 秒（轮询语义）与 100 万事件的 90 天清理尚未在本轮验证。
- 本机为单机容器；生产是 8 vCPU/24GB 服务器（Q23），需要在验收环境复测后写入结论。

## 9. 影子对比工具（M5）

实现：`src/testing/shadow-comparison.ts`（纯逻辑）、`src/testing/shadow-compare-cli.ts`（入口）、
`src/service-decision-sink.ts`（旧 worker 侧结构化证据落盘）。
命令：`npm run shadow:compare -- --sink=<证据.jsonl> [--since=ISO] [--threshold=0.02] [--json]`。
未通过时以退出码 2 结束，可直接放进自动化验收。

**数据面**：旧系统侧读 `--sink` 指定的 JSONL（由 `src/service.ts` 的决策回调写出，只写本地文件、
不连新系统库，Q32-B/Q42）；新系统侧读 `decisions` 表。

**对齐键**：归一化账号 + 上游事件时间（秒）——上游没有消息 ID（已核实），
两个系统各自生成的 ID 不可比；本地接收序号只作次序仲裁（Q31）。

**对比口径**（Q33、Q36、Q39、Q57）：

| 维度 | 口径 | 是否阻断 |
|---|---|---|
| 星级 | 双方“达到的星数”，未达门槛记为 0 | **是**（要求 100% 匹配） |
| 去重 | 归一为“是否被跳过”，不同原因码表达同一结论不算差异 | **是**（要求 100% 匹配） |
| 分类 | 只比 type；调用异常单独记为 classify_error；分母 = **旧系统实际分类过的样本数** | 差异率超阈值（默认 2%）才阻断 |

被排除的样本：旧 worker 重启窗口（内存去重集为空导致不可比，Q39）、合成/回放样本（默认不计入，Q57）。

**端到端验证**（合成数据，注入 1 条星级差异 + 1 条重启窗口样本）：
成功对齐 60 条、排除重启样本 1 条、**准确识别出 1 条星级差异并以退出码 2 阻断**。

### 9.1 本轮发现并修复的两个真实缺陷

1. **零对齐样本会被判定为“通过”**（假通过）。端到端验证时出现“仅旧 34 / 仅新 0”却输出通过。
   已改为：`matched === 0` 直接阻断——没有对比证据就不能判定通过。
2. **合成数据从未写入 `upstream_push_at_sec`**，导致影子对比在新系统侧一条都对齐不上
   （也正是上面假通过的成因）。已修正生成器的列与参数，并补上类型标注。
3. 顺带修正未对齐比例的计量口径：分母改为旧系统样本量（影子期旧系统才是权威执行者）。

## 10. 备份恢复演练（M5，已执行一次）

实现：`src/testing/backup-drill.ts`（编排与核验）、`src/testing/backup-drill-cli.ts`；
命令：`npm run drill:backup -- --source-url=<源库> --target-url=<空目标库> [--passphrase=...]`。

**本次执行环境**：本机 Docker `postgres:16-alpine`；新建源库 `djk_drill_src` 写入合成数据（300 账号 / 2000 事件），
目标库 `djk_drill_dst` 为空白库并先迁移到同一 schema 版本。

| 步骤 | 结果 |
|---|---|
| `pg_dump --format=custom` | 180 KB |
| AES256 加密（gpg 对称口令） | 130 KB，备份文件非空且校验通过 |
| 解密 + `pg_restore` 到空库 | 退出码 0 |
| 行数比对（10 张关键表） | 一致 |
| 内容指纹（全部接收记录的 event_id+去重键+push_at 摘要） | 一致 |
| 迁移版本比对 | 一致 |
| **RPO** | **49.5 分钟**（目标 ≤60 分钟）**达标** |
| **RTO** | **4.0 分钟**（目标 ≤120 分钟）**达标** |

关键口径：RPO 按**备份实际覆盖的数据时间点**（库内最新接收记录时间）计算，
不使用备份完成时间——后者会把 49.5 分钟错算成 0 分钟（第 10.1 节明确禁止）。

**尚未完成的部分**：

## 13. 运行指标增量计数（M5 发现并修复的瓶颈）

**问题**：第 12 节实测 `/api/health` 的 p50 为 31 ms，比列表查询还慢。
原因是 `readHealthSnapshot` 用多个 `count(*)` 子查询统计 `inbound_events` 与 `decisions` 全表。
数据量继续增长会直接拖慢运行状态页。

**处理**（迁移 `0011_runtime_counters.sql`）：
- 新增 `runtime_counters` 计数表，用**语句级触发器**在插入/删除后按影响行数更新一次；
- 用语句级而非行级：批量插入 5000 行时行级触发器会执行 5000 次，语句级只更新一次；
- PostgreSQL 不允许一条触发器同时为 INSERT 与 DELETE 指定 transition table，因此每种事件各建一条（实跑时暴露的限制）；
- 迁移内用绝对值回填一次，保证历史数据对齐；
- 只对事件与判定计数；项目/任务/投递仍实时统计——它们基数小且状态变化频繁，用计数器容易漂移；
- `readHealthSnapshot` 保留回退：计数行不存在时退回实时统计，绝不把 0 当成真实总量。

| 项 | 修复前 | 修复后 |
|---|---:|---:|
| `/api/health` p50（20 万事件） | 31 ms | **1.6 ms** |
| 插入后计数 vs 真实行数 | — | 一致（5000 / 5000） |
| 90 天清理后计数 vs 真实行数 | — | 一致（3767 / 3767） |

## 14. Worker 调度循环（M5 最后一块实现）

实现：`src/worker/loop.ts`（一轮调度 + 循环状态）、`src/worker/main.ts`（常驻入口，`npm run worker:start`），
7 个集成测试（`tests/worker-loop.test.ts`）。

**一轮调度做什么**：先领取并执行生成任务（含租约回收），再处理待投递，最后**按间隔**执行保留期清理。
顺序有意为先任务后清理：清理占用 I/O，放在后面避免拖延任务领取。

**关键设计取舍（都写进了实现注释与测试）**：

| 取舍 | 原因 |
|---|---|
| 清理默认最小间隔 1 小时 | 它按天级窗口生效，频繁跑只是浪费 |
| 清理未到间隔时**不刷新清理时间** | 否则永远到不了间隔（有专门断言） |
| 执行器整轮失败只记录、不抛出 | 常驻循环不该因一轮失败退出，下一轮重试 |
| 清理失败不影响任务结果 | 两者互相独立；清理下一轮再来 |
| `describeWorkerLoop` 暴露 `cleanupStale` | 超过两个间隔没有成功清理即需告警（Q101） |

**影子期安全默认值**：worker 入口的投递实现**默认抛错**（"投递未启用（影子模式）"），
只有显式设置 `TELEGRAM_DELIVERY_ENABLED=true` 才会真正发送 Telegram。
这与 Q32/Q87 一致：影子期新栈不得产生外部副作用。

**验证**：一轮内任务完成 1 个 + 清理删除 1 条过期记录；未到间隔时跳过且沿用上次清理时间；
到点后刷新清理时间；执行器整轮失败与清理失败都只记录错误不中断循环。

## 19. 前端首次真实使用暴露的两个缺陷（M4/M5）

用 Playwright 打开真实页面截图检查时，发现两个此前"测试全绿"没有抓到的问题。

### 19.1 健康接口喂给了面向列表的轮询 Hook（运行时错误横幅）

**现象**：工作台顶部长期显示 `数据服务异常：X.rows is not iterable`。
**原因**：`/api/health` 返回的是快照对象（没有 `rows`），`main.tsx` 的 `HealthStrip` 却用了为分页列表
设计的 `usePolling`（它会读取 `next.rows` 做版本去重），并且在 Milestone 4 实现时用 `as never`
**把类型错误压掉了**——因此 TypeScript 与单测都没拦住，只有真实浏览器渲染才暴露。
**修复**：改用 `usePolledValue`（按对象整体轮询），去掉 `as never` 与手写类型断言；
顺带把 `ExcludedPanel` 里为了绕开列表版本比较而人造的 `version` 字段一并去掉。
**回归防护**：浏览器验收新增检查项 **“页面无运行时异常横幅”**（现在共 5 项检查），
断言页面正文既不含“数据服务异常”也不含 `is not iterable`。

### 19.2 合成数据从未写入 `inbound_events.link`，导致所有项目“最近事件：无记录”

**现象**：项目池里每一行都显示“最近事件：无记录”。
**原因**：合成数据生成器为了省字段，把链接只写进了去重键，**没有写 `link` 列**；
而页面回填项目的首次/最近事件时间依赖 `link` 提取账号。真实流水线（`decision-recorder.ts`）
是写 `link` 的，所以这是**合成数据与真实路径的形状差异**，不是产品缺陷——但它会让演示与
基于合成数据的页面检查都失去意义。
**修复**：生成器写入 `link` 列（每行参数 9 → 10），并在事件批次写完后按 `link` 提取账号
回填 `projects.first_event_at` / `last_event_at`。
**实测**：801 个项目中 800 个有事件时间（其余 1 个是已排除项），页面显示“12 分钟前 / 22 小时前 / 4 天前”等真实相对时间。

### 19.3 顺带确认的两件事

- **“配置版本未记录”是数据缺失的如实表达**：合成数据不写 `config_version_id`，排查页逐条标注
  “配置版本未记录”，而不是伪造一个版本号——与 Q38/Q45 的口径一致。
- **“推特喊单”正确显示未配置**：数据源未配置时显示“数据源未配置：暂不展示内容”，
  不把“未检索”显示成“没有提及”（Q113/Q129）。

## 20. 合成数据的协议上限缺陷（跑 30 万事件时暴露）

**现象**：用 `batchSize=10_000` 生成 30 万事件时报
`bind message has 34464 parameter formats but 0 parameters`。
**原因**：PostgreSQL 扩展查询协议用 Int16 表示参数个数，**单个语句上限 32767**；
而每行 `inbound_events` 占 10 个参数，1 万行就是 10 万参数，超限。
**修复**：生成器显式收敛批量——
`POSTGRES_MAX_PARAMS_PER_STATEMENT = 32_767`、`INBOUND_EVENT_PARAMS_PER_ROW = 10`，
`clampBatchSize()` 把请求批量压到 `floor(32767 / 10) = 3276` 以内，并导出常量供测试断言。
**回归**：`tests/synthetic-dataset.test.ts` 新增两条用例，断言“请求 1 万行被收敛后参数数不超上限”
以及“非法输入退到安全值”。

这条与第 13 节的触发器限制、第 19 节的前端 Hook 误用一样，都是**只有把规模或场景推上去才会暴露**的问题：
测试全绿并不等于可以跑真实规模。


## 21. 上游连接实测：第二条连接会接管事件流（2026-09-14）

**实验背景**：为验证“上游 → 新栈流水线 → 数据库 → 前端”这条链路，我用
`src/worker/alpha-bridge.ts` 以同一钱包直连 Alpha WebSocket，并把收到的事件写入演示库。

**关键观察**：

| 连接 | 建立时间 | 监听时长 | 心跳 | 业务事件 |
|---|---|---:|---:|---:|
| 连接①（桥接） | 10:16 | 576 s | 19 | **0** |
| 连接②（探针，同钱包新登录） | 10:26:35 | 45 s | 1 | **1**（`A8猪脚饭 关注了 Roger\|Bluebird🕊️`） |
| 连接③（桥接，新登录） | 10:30 | ~240 s | — | **0** |

**推论**：业务事件只投递给**最近一次登录**的连接；心跳对旧连接仍照常广播。
因此旧连接（旧 worker）会呈现“进程健康、心跳正常、业务静默”的状态——**最难排查的一类故障**。

**证据强度（必须如实标注）**：样本量小，且上游本身事件密度低（现网真实数据只有 3 个项目、
`logs/daxinjiankong.log` 为 0 字节）。上述推论与观察一致，但**未被独立复现**。
它与“事件本来就稀疏、探针只是碰巧”这一竞争解释无法仅凭本机数据区分。
区分方法：核对生产 worker 日志与其 TG 频道在同期是否有推送——**由用户在服务器侧确认**。

**对迁移方案的影响（已经落到主规划）**：

1. 影子期**不得**让新栈再连一次上游；必须走 Q32-B 的本地 sink 路径。
2. “新旧并行观察”的窗口内，**任何额外的上游登录都会打断旧 worker 的推送**，
   因此停机窗口、运维操作、调试脚本都必须避免重复登录。
3. 该风险已固化为代码约束：`alpha-bridge.ts` 默认拒绝运行（退出码 3），
   必须显式 `--force`，并在启动时打印警告。

**未验证项**：上游是“按账号只投最新连接”还是“按连接轮询”，以及旧 worker 断线重连后
能否自动夺回事件流——这两点只能在生产侧观察确认。

## 22. 前端 P0：项目池游标分页与滚动加载（Q95，已实现）

**问题**：`nextCursor` 只存在于 `web/src/api.ts` 的类型定义里，界面完全没用它。
5 万项目的演示库**只能看到前 50 个，无法翻页**——这是前端最影响可用性的缺口。

**实现**：
- `web/src/state.ts` 新增 `appendPage()`（按 `projectId` 合并去重）、`canLoadMore()`、
  `describeLoadedCount()`、`advancePagination()`，以及组合轮询的 `usePaginatedList()`；
- 项目池改为**游标分页 + 滚动到底自动加载**（哨兵元素 + `IntersectionObserver`，提前 240px 触发），
  并保留"加载更多"按钮作为兜底；筛选条件变化时整体重置游标与已加载行；
- 轮询只刷新**第一页并合并**，不打断已加载的后续页；
- 长列表渲染按最佳实践加 `content-visibility: auto` + `contain-intrinsic-size`
  （滚动加载会累积成百上千行，跳过视口外行的布局与绘制）。

**实测（演示库 50,100 个项目，系统 Chrome）**：

| 轮次 | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 已加载行数 | 50 | 100 | 150 | 200 | 250 | 300 | 350 |

进度文案同步更新（"已加载 350 条，滚动到底继续加载"），控制台与网络**零错误**；
浏览器验收 5 项检查全通过（无异常横幅），列表 p95 147 ms。

### 22.1 过程中发现并修复的两个真实缺陷

这两个都**不是靠单元测试能发现的**，只有真实浏览器交互才暴露：

1. **加载在 100 条永久停住（请求被丢弃）**：轮询与滚动加载共用一条串行通道，
   我最初在通道忙时**直接 return 丢弃**了滚动加载请求。而哨兵元素此时仍停在视口内，
   `IntersectionObserver` 不会再触发（交集没有变化），于是加载永久卡住。
   修复：改为**排队**（`pendingMoreRef`），通道空出来后补做；末页用 `hasMore` 兜住避免空转。
2. **轮询每 2 秒把分页位置打回第 2 页（游标被覆盖）**：轮询刷新第一页时，
   第一页响应的 `nextCursor` 指向的是**第 2 页**；我用它覆盖了游标，
   导致滚动加载每次都重新取第 2 页（去重后行数不增长），表现为"到 100 条就不动了"。
   修复：抽出纯函数 `advancePagination()`，明确规定 **merge（轮询）不得改动分页位置**，
   并用测试固化该不变量（含"连续轮询 5 次后游标仍停在第 3 页"的回归用例）。
