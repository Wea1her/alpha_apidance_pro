# 前端迁移：压力测试与验收方案

日期：2026-09-13。

已完成：当前文件存储的受控并发复现、静态失效分析和架构一致性审查。

尚未执行：新 API、网页、PostgreSQL 任务系统的容量、延迟与恢复验收；这些组件尚未实现。下列指标来自已确认的设计目标，不是测试通过声明。

## 1. 已执行的并发复现

环境：Node.js v22.17.0。两个可复用子进程，共 12 次合成记录提交。数据全部位于新建的临时目录，不读取真实业务数据，不请求模型、Alpha 或 Telegram。

| 真实存储组件 | 顺序对照：预期 / 实际 | 受控交错：预期 / 实际 | 两次写入都返回成功 | 错误数 |
|---|---:|---:|---|---:|
| AnalysisArchiveStore | 2 / 2 | 2 / 1 | 是 | 0 |
| AnalysisTaskQueue | 2 / 2 | 2 / 1 | 是 | 0 |
| ProjectStateStore | 2 / 2 | 2 / 1 | 是 | 0 |

复现步骤：两个进程先实际读到同一份空文件；暂缓读取返回，让 A 完成写入；随后允许 B 根据之前读到的旧快照完成写入。最终保留 B，A 已获得成功回执的数据消失。

只控制了真实读取返回的时机，存储组件的校验、记录构造、写入与 rename 未替换。ProjectStateStore 用真实 `load → 修改 → save` 调用，证明调用方没有获得并发合并保护，不能把整体替换接口当作事务更新。

结论：进程内 Promise 锁与文件 rename 不足以保护多写入者的业务更新。多个浏览器只读本身不会造成这个覆盖问题，但拆出 API/worker、多实例或新增写入口后会暴露它。

这证明一种可发生的丢失更新交错，不表示生产发生频率，也不是吞吐压测。

复现脚本：[reproduce.mjs](probes/file-store-concurrency/reproduce.mjs)。完整结果及被测源码哈希：[result.json](probes/file-store-concurrency/result.json)。

在仓库根目录执行：

```bash
node docs/architecture/probes/file-store-concurrency/reproduce.mjs .
```

需要支持 TypeScript 类型擦除的 Node 22.17 或兼容版本。每次生成独立临时目录，输出实际结果位置；不会改写项目的 `data/` 文件。未来源码改变时以输出的源码哈希和实际结果为准，不把旧复现结论套到新实现。

## 2. 已确认的容量与体验目标

| 指标 | 目标 | 计量边界 |
|---|---|---|
| 同时在线 | 10 个独立登录用户 | 每个用户具有列表查询和实时连接 |
| 保留数据 | 100 万条业务接收记录 | 分布于 90 天，含重复、过滤、未达门槛和通过记录 |
| 入站峰值 | 每秒 20 条，连续 60 秒 | 60 秒是本方案对“短时”的测试定义；模型任务可排队 |
| 列表查询 | p95 ≤ 1 秒 | 记录 API 请求与浏览器列表更新的端到端时长；不能仅用数据库耗时代替 |
| 状态可见性 | ≤ 3 秒 | 数据库提交可展示状态，到在线浏览器显示；不包含模型生成耗时 |
| 数据丢失目标 | ≤ 1 小时 | 故障时间与实际可恢复的数据时间点之差 |
| 服务恢复目标 | ≤ 2 小时 | 从开始故障恢复演练到数据校验完成、网页可用且后台恢复工作 |

记录测试服务器、负载客户端、网络条件、提交版本和样本数。起始服务器建议 2 vCPU、4 GB RAM、SSD；指标是否可达必须实测，不能凭规格推定。

## 3. 容量验收方法

1. 在隔离数据库生成 100 万条合成业务接收记录、10 万个账号，以及标准/深度报告、任务与投递历史。固定随机种子，混合普通账号和热点账号；保留重复、解析失败及分类失败后放行等边界样本。
2. 按真实索引与保留结构运行，不用缩减的内存数据替代。先测冷启动，再热身 2 分钟，执行 15 分钟混合查询。
3. 10 个独立登录客户端持续在线。每个客户端平均每 2 秒发起一次查询，混合列表分页、账号精确搜索、星级/状态筛选和项目详情；同时维持 SSE。
4. 背景持续接收每秒 1 条事件，中途以每秒 20 条持续 60 秒制造高峰，同时写入合成任务和投递状态。
5. 使用可控模型与 Telegram 适配器，分别模拟短分类、普通分析、慢深度分析与失败；不对真实模型或频道施压。
6. 捕获列表 p50/p95/p99、错误率、状态可见延迟、队列最老等待时间、数据库锁等待、内存和磁盘占用。入站成功提交计数必须与可查询记录数一致。
7. 在新增数据期间反复翻页，核验稳定游标不漏不重。对热点账号验证有序判定以及只创建一个首次标准、一个首次深度任务。
8. 执行 90 天清理和一次备份，确认交互仍满足目标、长期报告仍可读、正在投递的正文与线程引用完整。

负载生成可采用 Node 或 k6，浏览器交互采用 Playwright；在实现阶段固定版本和场景脚本。首次压测失败时先依据查询计划、锁等待和任务积压定位，再决定优化或增加资源。

## 4. 必须通过的故障验收

| 编号 | 注入条件 | 必须观察到的结果 |
|---|---|---|
| F1 | 两个 worker 同时领取同一业务意图 | 只有一个当前持有者，重复创建由数据库约束拒绝；其他任务不丢失 |
| F2 | 同一账号的后续 5 星事件先完成模型请求 | 持久化判定顺序保证首个符合规则的事件拥有深度任务，后续不能抢占线程 |
| F3 | 模型超时、worker 中止、租约过期后旧进程返回 | 请求有截止时间，任务可回收；旧执行代次不能覆盖新结果 |
| F4 | 标准或深度正文已经落库后 Telegram 失败 | 网页完整展示正文，后续补发不再次调用已保存正文的模型任务 |
| F5 | Telegram 长时间整体不可用，或讨论映射缺失 | 分析继续；投递进入依赖等待，不逐条耗尽预算；恢复后自动唤醒并补发 |
| F6 | Telegram 已收消息但本地回执丢失 | 记录不确定尝试，按已确认策略继续补发；允许重复但不能隐藏尝试历史 |
| F7 | 单条消息配置错误或重试预算耗尽 | 明确告警和待处理状态；服务器端修复与重放保持原意图和分片，不依赖新增网页写操作 |
| F8 | 两个数据库事务乱序提交、feed 发布中途崩溃 | 对外游标不会漏掉晚提交事务；feed 与 outbox 发布标记同事务，重连可以补拉 |
| F9 | 浏览器断网、重复标签页、SSE 游标过期 | 从持久化状态恢复，过期时重取快照；不会重新触发模型或 Telegram |
| F10 | 90 天清理遇到长期报告或未完投递 | 外键不级联删除报告、任务和投递；来源摘要可读，原事件显示过期 |
| F11 | 数据库不可用、磁盘满、坏数据 | 显示数据或采集异常，不伪装成“没有项目”；未提交事件不计为安全保存 |
| F12 | 模型供应商鉴权失效 | 无效请求停止反复消耗资源；分类仍按既有策略标记异常并保守放行；生成任务等待修复 |
| F13 | 429 与可恢复错误 | 尊重等待时间并退避，记录真实物理请求次数；依赖等待不冒充模型失败 |
| F14 | 用户未登录、邀请重复兑换、权限撤销 | 访问被正确限制；同一邀请只成功一次；撤销后 API 与已有 SSE 均失效 |
| F15 | 报告含 HTML、脚本或不安全链接 | 页面仅安全渲染文本/Markdown，不执行模型或上游提供的脚本 |

每个场景都保存事件 ID、任务 ID、投递 ID、数据库状态快照和时间线。只看到 HTTP 200 或进程仍在运行，不能算恢复验证通过。

## 5. 备份恢复演练

1. 持续写入带可识别序号和提交时间的合成事件，并生成报告和未完成分片投递。
2. 按部署策略生成加密备份并上传到服务器外，记录备份包含的实际数据时间点。
3. 模拟原服务器不可用，在空环境从服务器外副本恢复数据库、配置与程序，不读取原机数据目录。
4. 核验账号数、报告内容摘要、唯一任务约束、待投递分片及线程引用。旧会话和未使用邀请失效，管理员可以重新登录。
5. 检查最新可恢复事件与故障时间的差值 ≤ 1 小时；检查整体恢复 ≤ 2 小时。上传成功时间较新不代表备份包含的数据足够新。
6. 恢复后台，验证积压任务继续工作、已保存报告不重新生成；对可能重复的外部投递如实记录。
7. 演练备份上传失败和损坏副本，确认能告警并选择有效副本。没有通过恢复验证的文件不能算合格备份。

## 6. 切换与回退验收

- 用现有合成事件回归星级阈值、分类放行/拦截、失败保守放行、升星重复规则和深度一次性规则。
- 导入历史 JSON/JSONL 时只迁移事实，不编造缺失的原始事件、分类理由或生成时间；不发生模型请求和 Telegram 发送。
- 影子采集/判断阶段禁止产生第二套外部副作用；切换时核验只有一个激活业务执行者。
- 保留旧记录到新业务 ID 的映射；核验标准提醒仍指向原分析评论，深度报告仍对应首次合规 5 星的频道线程。
- 新数据库产生写入之后，回退必须保留这些增量；不能以直接启用旧 JSON 目录作为无损回退方案。
- 记录切换观察空窗。当前无法保证 Alpha 回放，不能声称所有上游缺失事件会自动补齐。

## 7. 验收报告应包含什么

交付测试环境、代码版本、种子数据、场景脚本、延迟分位数、错误率、任务/投递完整性统计、故障时间线、实际恢复点与恢复时长。
